# 04. Обязательные требования к экономии токенов DeepSeek API

**Статус:** обязательная часть ТЗ и рабочего процесса.  
**Применение:** каждый вызов DeepSeek API, связанный с анализом, проектированием, генерацией кода, исправлениями и тестированием ForgeDesk.

## 1. Цель

Сократить расход входных и выходных токенов, стоимость вызовов, дублирование анализа и объём повторно передаваемого контекста, не ухудшая качество кода, полноту проверок и надёжность продукта.

Экономия токенов — не повод пропускать необходимые проверки, скрывать ошибки, упрощать безопасность или генерировать неполный код. Цель — не передавать модели то, что ей не нужно для текущей задачи.

## 2. Обязательные правила контекста

### 2.1. Не перечитывать весь проект на каждом шаге

- Полную инвентаризацию репозитория выполнять один раз на Stage 0.
- Результаты записывать в компактные `docs/architecture/repository_map.md`, `docs/architecture/overview.md`, `docs/decisions/` и `docs/PROJECT_STATE.md`.
- На последующих этапах читать только изменённые и непосредственно связанные файлы.
- Не выполнять повторный полный listing/grep/read всего репозитория без причины.
- Повторно исследовать файл, если он изменился, его содержимое неизвестно, тест обнаружил несоответствие или решение зависит от актуального кода.

### 2.2. Целевой сбор контекста

Перед задачей определить минимальный контекст:
1. соответствующий раздел ТЗ;
2. относящиеся ADR/architecture notes;
3. релевантные исходные файлы и их непосредственные зависимости;
4. тесты для затрагиваемой функциональности;
5. актуальный `PROJECT_STATE.md`.

Не прикладывать весь кодовый архив, если задачу можно выполнить по 3–8 конкретным файлам. Не читать ресурсы/сборочные артефакты/бинарные файлы без явной необходимости.

### 2.3. Не дублировать уже известные требования

- Не пересказывать пользователю всё ТЗ перед каждым этапом.
- Не включать полный текст базовых спецификаций в каждый последующий запрос, если оркестратор может передать ссылки/файлы или повторно отправить один и тот же кешируемый префикс.
- В каждом этапе передавать краткую ссылку на обязательные документы и только актуальные требования конкретной задачи.
- Не запрашивать повторно сведения, которые уже есть в README, ADR, PROJECT_STATE или текущем контексте.

### 2.4. Не отправлять избыточные логи

При диагностике прикладывать:
- команду;
- результат exit code;
- первые/последние релевантные строки ошибки;
- несколько строк контекста вокруг ошибки;
- точный путь к файлу и номер строки, если известен.

Не передавать полный успешный build/test log. Для больших логов сначала выполнять локальную фильтрацию по `error`, `warning`, test name, panic и stack trace. Полный лог нужен только при доказанной необходимости.

## 3. Экономия при генерации и изменении кода

- Выдавать минимальный unified diff или patch, а не полный файл, если пользователь/инструмент может применить diff и контекст однозначен.
- Полный файл допустим только для нового файла, небольшого файла или когда точечный diff ненадёжен.
- Не повторно генерировать уже существующий и проверенный код.
- Не менять несвязанные файлы ради стилистической унификации.
- Не проводить крупный рефакторинг одновременно с функциональной задачей без отдельного основания.
- Использовать существующие модели, сервисы, компоненты, функции, helpers и зависимости вместо дублирования.
- Не создавать новую библиотеку/helper/абстракцию, если подходящая уже есть.
- Перед добавлением новой зависимости проверить, нет ли в проекте аналога.
- Изменять один логически связанный набор файлов за итерацию; не дробить одну атомарную функцию на искусственно большое количество вызовов.
- Не добавлять boilerplate, комментарии или документацию, которые повторяют очевидный код; комментарии должны объяснять причины, ограничения или нетривиальные решения.
- Не генерировать лишние варианты реализации, если архитектурное решение уже зафиксировано.

## 4. Экономия на тестировании

- Во время локальной итерации запускать сначала только тесты затронутого модуля/функции.
- Полный набор тестов запускать на контрольной точке этапа, перед merge/release или при затрагивании общих контрактов.
- Не повторять один и тот же успешный тест без изменения кода/окружения, которое может повлиять на результат.
- Не пропускать тесты, которые прямо требуются acceptance criteria.
- Не ослаблять тест, чтобы он проходил.
- Сохранять результат контрольных тестов в `docs/PROJECT_STATE.md` или stage report с commit hash/working tree revision, командой и результатом.
- При следующем вызове не просить модель заново запускать те же проверки, если с тех пор не менялись затронутые исходники, тесты или среда.

## 5. Постоянная компактная память проекта

DeepSeek должен поддерживать несколько небольших файлов состояния. Они заменяют повторную передачу больших историй диалога.

### `docs/PROJECT_STATE.md`

Не более примерно 1–2 экранов текста (цель — до 1 500–2 000 токенов). Содержит:
- текущий этап и цель ближайшей итерации;
- текущую архитектуру;
- что уже реализовано;
- последние изменения и файлы;
- тесты, которые прошли, с точной командой;
- известные проблемы;
- следующий конкретный шаг;
- открытые решения (только реальные блокеры).

### `docs/architecture/repository_map.md`

Компактная карта директорий и назначение ключевых модулей. Обновлять только при изменении структуры.

### `docs/decisions/`

Краткие ADR: проблема, выбор, последствия, альтернативы, дата. Не копировать туда всё обсуждение.

### `docs/stages/STAGE-N-report.md`

Короткий отчёт по этапу: scope, changed files, tests, known limitations, commit/revision.

Не хранить стенограмму всех вызовов DeepSeek. Сохранять только решения и проверяемое состояние.

## 6. Формат результата каждого вызова

По умолчанию DeepSeek должен возвращать краткий итог в следующем виде:

```text
STATUS: DONE | PARTIAL | BLOCKED
SCOPE: <one-line objective>
CHANGED:
- path/to/file — one-line reason
TESTS:
- command — PASS/FAIL/SKIPPED (reason)
RISKS:
- only real remaining risks
NEXT:
- one concrete next task
```

Не повторять текст ТЗ, не выдавать полную архитектуру повторно, не печатать содержимое всех изменённых файлов, если пользователь запросил патч/изменение файлов.

Если задача не выполнена полностью, прямо указать, что не сделано. Не маскировать `PARTIAL` под `DONE`.

## 7. Правила против лишних уточнений

- Не превращать реализацию в длинное интервью.
- Не спрашивать пользователя о выборе имён переменных, методов, компонентов, цветов, внутренних библиотек и расположении файлов, если это не меняет продуктовые свойства.
- При неоднозначности выбрать самый простой безопасный вариант из текущей архитектуры и записать решение в ADR/assumptions.
- Вопрос задавать только если без ответа невозможно безопасно выполнить задачу или выбор существенно влияет на формат данных, удалённые ресурсы, безопасность, права или необратимые действия.
- Не спрашивать повторно уже подтверждённые решения: single-user, local-first, SQLite, отсутствие backend, AI optional, GitHub deep integration, Windows/Linux, GraphQL-first with REST fallback.

## 8. DeepSeek API prompt caching

По состоянию на дату подготовки DeepSeek API документирует автоматический context caching. Кэширование — best effort, не гарантия; оно лучше работает при совпадающем префиксе. В usage могут приходить `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens` (в Chat Completions/совместимых ответах) или эквивалентные cache usage fields.

Для повышения вероятности cache hits:
- держать постоянными system/warm prompt и общую неизменную часть проектной спецификации;
- передавать документы в одинаковом порядке;
- не вставлять динамические timestamps, случайные IDs, текущие логи или меняющийся PROJECT_STATE в начало статического префикса;
- располагать статический проектный контекст первым, меняющуюся задачу и актуальные файлы — после него;
- не переписывать system prompt стилистически от вызова к вызову;
- не менять формулировки большого постоянного prompt без необходимости;
- сохранять точный текст warm prompt и стабильный порядок документов.

Важно: контекстный кэш может уменьшить стоимость/задержку повторяющегося префикса, но сам по себе не уменьшает длину контекста и не заменяет удаление нерелевантного текста. Не считать кэш гарантированным и анализировать фактические usage fields.

### Метрики DeepSeek

Если используем DeepSeek API orchestrator, логировать без содержимого кода:
- input/prompt tokens;
- output/completion tokens;
- cached input tokens / cache hits;
- cache misses;
- reasoning tokens, если доступны;
- модель и этап;
- длительность и стоимость (если API возвращает/можно вычислить по актуальному прайсу).

Не передавать секреты/приватный код в стороннюю аналитику. Usage log должен быть локальным и отключаемым.

### Stateless API context

Не рассчитывать на серверную память диалога или на то, что DeepSeek сам восстановит все предыдущие ходы. Контекст конкретного этапа передаётся через закреплённый prompt, пакет документов и компактный PROJECT_STATE. Не отправлять всю историю переписки, если нужные решения уже вынесены в документы.

## 9. Экономия токенов и качество — баланс

Запрещено ради экономии:
- исключать обязательную валидацию;
- сокращать обработку ошибок;
- опускать security checks;
- не писать тесты для критических алгоритмов;
- выдавать псевдокод вместо запрошенной реализации;
- делать невидимые изменения поведения;
- скрывать неполное выполнение;
- сокращать документацию так, чтобы потерялись важные контракты.

Экономить нужно на повторении контекста, нецелевом чтении, избыточных логах, полных файлах вместо diff, повторных тестах без изменения условий и многословных объяснениях.

## 10. Checklist перед отправкой запроса DeepSeek

- [ ] Один конкретный результат сформулирован.
- [ ] Переданы только относящиеся к нему требования.
- [ ] PROJECT_STATE актуален.
- [ ] Не включена повторно вся история переписки.
- [ ] Список файлов ограничен областью изменения.
- [ ] Большие логи предварительно сокращены.
- [ ] Статический prefix совпадает с предыдущими запросами для использования cache.
- [ ] Выбран ожидаемый краткий формат результата.
- [ ] Не поставлено несколько независимых больших задач в один запрос.

## 11. Экономия токенов при UI-разработке

- `06_UI_UX_SPEC.md` является единственным полным источником UI-контракта. Не копировать весь документ в каждый запрос. Передавать номера нужных разделов и краткий перечень критериев текущего UI Gate.
- Design tokens должны быть реализованы один раз в центральных theme files. Не дублировать палитру/spacing/typography в каждом компоненте и каждом prompt.
- Создать компактную `docs/ui/component_map.md` с компонентом, путём, назначением и основными props. После этого не перечитывать все frontend-компоненты при каждом изменении.
- Создать `docs/ui/visual_baseline.md` с viewport, theme, screenshot filenames и результатами последнего visual gate. Не пересылать все прошлые скриншоты повторно, если задача затрагивает отдельный компонент.
- Для UI-задачи передавать только: релевантные разделы `06_UI_UX_SPEC.md`, `PROJECT_STATE.md`, component map и затронутые компоненты/tests.
- Не генерировать новые макеты/скриншоты для каждого мелкого CSS-изменения. Снимки делать на границах UI Gate и при изменении геометрии/общего компонента.
- Не повторять визуальную приёмку неизменённых экранов после локального изменения несвязанного компонента. Повторять её при изменении shared tokens, AppShell, shared component или затронутого layout.
- Не создавать дублирующие компоненты и стили ради краткосрочной экономии времени: повторное дублирование увеличивает будущий контекст и стоимость поддержки.
- В stage report перечислять только затронутые screenshots и visual checks; не вставлять изображения или полные CSS-файлы в текстовый отчёт без необходимости.

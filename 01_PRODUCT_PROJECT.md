# 01. ForgeDesk — проект продукта

## 1. Резюме

ForgeDesk — локальная desktop-среда индивидуального разработчика для управления задачами, проектами, планированием, репозиториями, GitHub Issues, Pull Requests, code review, CI и релизами.

По пользовательскому охвату ForgeDesk должен предоставлять функциональность, сопоставимую с основными возможностями полной версии Linear: Issues, Projects, Initiatives, Cycles, custom views, Documents, Inbox/Triage, Insights, Dashboards, Roadmap, workflow и automations. Корпоративные multi-user и SaaS-функции, не имеющие ценности для одного пользователя, исключаются.

ForgeDesk не является веб-сайтом, обёрткой над GitHub или клоном Kanban. Его цель — обеспечить единое локальное рабочее место, связывающее намерение (задача), план (проект/цикл), исходный код (локальный Git), удалённые изменения (GitHub PR) и результат (merge/release).

## 2. Продуктовые принципы

1. **Local-first.** Локальная БД — основное хранилище внутренней модели приложения. Приложение полностью работоспособно без сети.
2. **Single-user by design.** Не проектировать роли, совместное редактирование, presence, организации пользователей, billing или серверную многопользовательскую синхронизацию.
3. **GitHub-native, provider-neutral.** GitHub — наиболее полный провайдер и основной сценарий; доменная модель не должна зависеть от GitHub-специфичных ID и типов.
4. **API-quota aware.** Необходима отдельная подсистема бюджетирования запросов и синхронизации; нельзя считать квоты бесконечными.
5. **AI optional.** AI-функции можно полностью отключить и исключить из сборки. Core не должен содержать обязательных AI-зависимостей.
6. **Offline-first UX.** Локальное изменение отображается немедленно; удалённая синхронизация выполняется позже.
7. **No unnecessary infrastructure.** Один desktop runtime, одна SQLite база, локальные файлы и внешние API по необходимости.
8. **Incremental implementation.** Продукт создаётся вертикальными этапами, каждый из которых собирается и тестируется отдельно.
9. **Fast interaction.** Клавиатурная навигация, command palette, быстрые формы, виртуализация длинных списков.
10. **Data ownership is explicit.** Для каждой связанной сущности и каждого синхронизируемого поля определён источник истины.

## 3. Целевая аудитория и сценарии

Целевой пользователь — один разработчик, который ведёт несколько собственных проектов и репозиториев, использует GitHub как основной Git-хостинг и локально запускает IDE/терминал. Приложение также должно поддерживать self-hosted GitLab и Gitea на базовом функциональном уровне.

### Основной сквозной сценарий

1. Пользователь открывает ForgeDesk. Интерфейс сразу загружает последнее локальное состояние.
2. Приложение при наличии сети запускает ограниченную синхронизацию, учитывая API-budget.
3. Пользователь открывает Project, например `EXHI Capture`.
4. Проект связан с одним или несколькими локальными путями репозиториев и удалёнными репозиториями.
5. Пользователь создаёт Local Issue, задаёт описание, приоритет, статус, labels, критерии приёмки, зависимости и подзадачи.
6. При необходимости пользователь явно связывает задачу с существующим GitHub Issue или публикует её как GitHub Issue.
7. Из карточки задачи создаётся локальная ветка. Перед операцией приложение проверяет Git status и сообщает о незакоммиченных изменениях.
8. Пользователь работает в IDE/терминале; ForgeDesk может показать локальный branch/status/commits.
9. При создании PR ForgeDesk связывает его с задачей по ID в имени ветки, коммите или PR body; пользователь может подтвердить/исправить связь.
10. PR, review, CI checks и merge status показываются в контексте задачи.
11. После merge automation rule может перевести задачу в Done. Автоматизация должна быть настраиваемой и видимой в журнале.
12. Прогресс проекта, milestone, cycle и dashboard пересчитывается на основании локальной модели.

### Сценарий работы без сети

Без интернета доступны: задачи, проекты, документы, сохранённые представления, фильтры, поиск, локальная история, вложения, локальные Git-команды, создание/изменение Local Issues, экспорт и резервное копирование. Внешние действия помещаются в outbox только после явного действия пользователя; интерфейс показывает статус `Pending sync`.

## 4. Функциональный охват

### 4.1 Issues / Tasks

Поля задачи:
- стабильный локальный ID;
- человекочитаемый идентификатор вида `FD-123` (уникальный в workspace);
- title и Markdown description;
- status и status category (`backlog`, `unstarted`, `started`, `completed`, `canceled`);
- priority (`none`, `low`, `medium`, `high`, `urgent`);
- type (`bug`, `feature`, `task`, `improvement`, `chore`, `research`);
- labels (много);
- estimate (необязательная числовая шкала);
- start date, due date;
- project, milestone, cycle;
- parent issue;
- source (`local` или provider-backed);
- external links;
- created/updated/completed timestamps;
- archived/deleted state (мягкое удаление там, где это разумно).

Операции: быстрое создание, редактирование, массовые изменения, дублирование, шаблоны, архив, comments, attachments, activity, watchers (в single-user смысле — локальная отметка наблюдения), подзадачи произвольной вложенности с контролем циклических связей, relations (`blocks`, `blocked_by`, `related`, `duplicate`).

### 4.2 Workflow

Пользовательские статусы и переходы. Каждый статус имеет категорию, цвет, порядок, флаг завершения. Не зашивать конкретную доску или workflow. Поддерживать несколько workflow-профилей, если это не усложняет первую версию чрезмерно; минимум — один на workspace с возможностью настройки.

### 4.3 Views

Виды: List, Board, Table, Calendar, Timeline. Общий движок фильтров и сортировки. Фильтры должны поддерживать AND/OR, группы условий, сравнения, пустые/непустые значения, даты и relation-поля. Saved Views хранят фильтры, сортировки, группировки, видимость колонок и плотность. Представления не создают копии задач.

### 4.4 Projects

Проект содержит описание, статус, приоритет, даты, milestones, связанные issues, repositories, documents, PRs, внешние зависимости и журнал активности. Поддержать project templates. Прогресс настраивается: count-based, estimate-based, milestone-based или manual.

### 4.5 Initiatives

Уровень над проектами. Инициатива объединяет проекты, имеет цель, статус, временные рамки и агрегированный прогресс. Иерархия: `Initiative → Project → Milestone → Issue → Sub-issue`.

### 4.6 Cycles

Рабочие циклы с датами начала/окончания, ручным или повторяющимся расписанием, назначением задач, переносом незавершённых задач, оценкой объёма и аналитикой velocity/burndown/burnup. Cycles доступны для одного разработчика, без командной модели.

### 4.7 Documents

Markdown-документы с заголовками, списками, таблицами, кодовыми блоками, изображениями/вложениями и ссылками на Issues/Projects/Initiatives/Repositories. Шаблоны, история изменений, поиск, импорт/экспорт Markdown. Хранение — SQLite плюс управляемое локальное файловое хранилище для больших вложений.

### 4.8 Inbox и Triage

Inbox собирает изменения локальных задач и внешних событий: упоминания, comments, новые/обновлённые Issues/PR, review requests, CI failures, синхронизационные ошибки. Triage — отдельная очередь разбора новых GitHub Issues и локальных входящих задач. Пользователь может принять, отклонить, объединить с дубликатом, назначить проект/приоритет/labels.

### 4.9 Insights и Dashboards

Метрики: cycle time, lead time, throughput, velocity, backlog age, completion rate, project progress, PR lead time, review time, CI success rate. Пользователь собирает дашборды из виджетов. Все значения рассчитываются на основе локальных данных и синхронизированного Git-кэша; рядом должны отображаться дата актуальности и неполнота данных.

### 4.10 GitHub

Глубокая интеграция через GraphQL в качестве основного API. REST — для недостающих операций и полезных возможностей (в частности, conditional GET/ETag). Возможности:
- авторизация GitHub App user access token;
- выбор доступных организаций и репозиториев;
- репозитории, metadata, branches, commits, tags, releases;
- GitHub Issues, labels, comments, milestones;
- Pull Requests, reviews, review comments, changed files/diff по запросу;
- CI checks / check runs / workflow runs по поддерживаемым API и разрешениям;
- GitHub Projects V2: минимум чтение/связь и базовые операции в отдельном этапе;
- локальные и внешние связи между объектами;
- импорт/экспорт и управляемая синхронизация.

### 4.11 GitLab и Gitea

Архитектура provider adapters. В первой версии после GitHub — базовые репозитории, issues, merge/pull requests, branches, commits, labels, comments, releases и pipeline/check status там, где API провайдера поддерживает их. Каждая возможность объявляется через capabilities. Отсутствующую функцию нельзя имитировать или молча пропускать.

### 4.12 Local Git

Использовать системный Git executable. Определять версии, проверять доступность, привязывать локальные каталоги к remote repositories. Команды запускать через аргументы процесса, не через shell interpolation. Поддержать status, current branch, branch list, create/switch branch, log, diff summary, open folder in IDE/terminal. Push/merge/reset/stash и потенциально разрушающие команды — только отдельным подтверждённым действием. Не выполнять auto-push.

### 4.13 Automations

Правила `trigger → conditions → actions`. Триггеры локальных событий и поддерживаемых Git-provider событий: status changed, PR opened/ready/merged, review requested/changes requested, CI failed/succeeded, release published, due date reached. Условия AND/OR. Действия: изменить локальный статус/priority/labels, добавить activity entry, создать inbox item, обновить project/cycle aggregation, при наличии отдельного разрешения выполнить удалённое действие. Каждое выполнение логируется, имеет deduplication key и защиту от рекурсивного цикла.

### 4.14 AI Extension (необязательный)

AI Assistant, генерация плана/подзадач/acceptance criteria/PR description, интеграции с DeepSeek/OpenAI/Anthropic, MCP/Agent Bridge. Модуль можно полностью отключить в UI и исключить из сборки. Core не зависит от него. В выключенном состоянии нет запросов к AI, фоновых процессов, MCP endpoint, хранения AI credentials или AI-навигации. Любые действия AI, изменяющие локальные или удалённые данные, требуют явного разрешения или отдельной пользовательской automation policy. Не включать AI по умолчанию.

## 5. UI / UX — обязательный контракт реализации

UI нельзя проектировать по общему описанию или на усмотрение исполнителя. Полная обязательная спецификация находится в `06_UI_UX_SPEC.md`; она определяет геометрию окна, размеры областей, палитру Dark/Light, типографику, spacing, навигацию, все основные экраны, поведение компонентов, состояния, горячие клавиши и визуальные критерии приёмки.

Ключевое направление:
- Desktop-first, рабочий viewport 1440×900 px; минимум 1100×700 px.
- Shell: native title bar, sidebar 240 px (collapsed 64 px), верхний app header 48 px, основная рабочая область и открываемая по запросу правая Detail Pane 440 px; на узких окнах Detail Pane становится overlay.
- Основной стиль: графитовая Dark theme с умеренным фиолетовым акцентом; полноценная Light theme.
- Плотная рабочая компоновка в духе Linear, технические экраны PR — с GitHub-native информационной структурой.
- Фиксированная sidebar navigation и определённая в `06_UI_UX_SPEC.md` структура экранов.
- Все основные состояния (loading/empty/error/offline/stale/pending) обязательны.
- Command Palette, keyboard-first workflow, List/Board, Issue Detail Pane и API Monitor — обязательные интерфейсные элементы.
- Русская и английская локализации; системная локаль по умолчанию, English fallback.

`06_UI_UX_SPEC.md` является обязательным, а не справочным документом. При любом расхождении между общим описанием UI в этом документе и точными размерами/компоновкой в `06_UI_UX_SPEC.md` приоритет у `06_UI_UX_SPEC.md`. DeepSeek не вправе менять визуальную идентичность, shell geometry, nav order, screen composition или density без ADR и согласования пользователя. Компилирующийся экран без screenshot-based review не считается принятым.

## 6. Исключения

Не реализовывать:
- multi-user collaboration, роли, SAML/SCIM, корпоративное управление;
- облачную собственную базу или сервер;
- обязательный AI;
- обязательную телеметрию;
- Slack/email customer intake в первой версии;
- hosted coding agent;
- встроенный полноценный редактор кода/IDE;
- автоматическое скачивание всех репозиториев;
- автоматический push/merge без отдельного разрешения;
- полную копию всех данных GitHub по умолчанию.

## 7. Нефункциональные цели

- Базовые локальные действия ощущаются мгновенными; UI не ждёт сетевого ответа.
- Старт приложения использует локальную БД и не блокируется доступностью GitHub.
- Устойчивость при закрытии приложения во время синхронизации.
- Транзакционность локальных изменений.
- Предсказуемые миграции БД.
- Восстановление из backup.
- Нет секретов в логах, crash reports и файлах конфигурации.
- Windows и Linux — целевые платформы первой версии.
- Внешние запросы идут только по явно подключённым интеграциям.
